# Local case format — single source of truth

> Owner: `test-documentation-local`. Cited by `test-automation-local`. The script `scripts/qa-local.ts` enforces this contract (`bun run qa:local check`); when prose and script disagree, the script's behaviour is what happens and the prose is the bug to report.
> Jira, Xray and TMS sentences in any reference cited from here do NOT apply: this format replaces them.

The QA root is a gitignored folder of the project (default: the `QA` folder inside the project's `.context` tree, overridable with `--root`). Layout, written once here and referred to as "the QA root" elsewhere:

```
<qa-root>/
  cases/<PREFIX>/<ID>.md          one file per manual-test case (given; the skills update them)
  prioridad-automatizacion.md     wave index (converter-owned, read-only for the skills)
  prefijos.md                     module prefixes of the project (table Prefijo | Modulo | Alcance), owned by test-case-generation-local
  estado.md                       GENERATED by `qa:local index`; never hand-edited
  automation/<scope>/             automation plans (written by test-automation-local)
  runs/<date>-<scope>/            run.json + run.md written by `qa:local results`
  bugs/<ID>-BUG-<n>/              one folder per product defect found during automation (report + evidence); owned by `bug-report-local`
  _tools/                         the converter that produced the case files
```

## 1. Case file

A case is `cases/<PREFIX>/<ID>.md`: simple `key: value` frontmatter between two `---` fences, then a Markdown body. Line endings of the file are preserved by every write.

### 1.1 Frontmatter fields that exist in every file (never renamed)

| Field | Meaning | Allowed values |
|---|---|---|
| `id` | case id; equals the filename | `<PREFIX>-<n>` |
| `bloque`, `seccion`, `funcionalidad`, `riesgo_mapa`, `origen` | provenance and grouping, user-owned | free text |
| `tipo` | scenario type, free text with combinations | e.g. `P`, `N`, `S`, `R`, `L/N`, `NF`, `E2E`, `Smoke`, `UAT` |
| `prioridad` | priority, user-owned | `A`, `M`, `B` |
| `ola` | wave, user-owned; `0` = no wave | integer >= 0 |
| `automatizacion` | the VERDICT | `candidate`, `manual`, `deferred`, `no_aplica` |
| `automatizacion_motivo` | reason for any verdict other than `candidate` | text |
| `estado_automatizacion` | the LIFECYCLE | `pendiente`, `en_automatizacion`, `automatizado` |

A case is its id, scenario and expected result. The manual-run state of the user's matrix is not an input of this flow: every case is tested again from scratch. Legacy files that still carry old manual-run fields are tolerated and ignored (never validated, never gating).

Required for `check`: `id`, `ola`, `prioridad`, `tipo`, `automatizacion`, `estado_automatizacion`.

### 1.2 Optional fields added by the skills (absent in untouched files)

```yaml
precondiciones: ""        # business-level text, from design
datos: []                 # variable NAMES needed; never a secret value
automation: {surface: e2e, spec: "", atc: ""}   # surface is e2e or api; set through qa:local status / results
oraculo: historia         # provenance of the expected result: historia | observado | confirmado; written by `qa:local case new` / `case confirm`
id_defecto: ""            # defect reference; written ONLY by qa:local defect, after a failing automated run
defecto_conocido: true    # written ONLY by qa:local defect
roi: {frequency: 0, impact: 0, stability: 0, effort: 0, dependencies: 0, bonus_n: 0, prior_bug: false, score: 0}   # only when a verdict is CHANGED
last_run: {date: "2026-01-31", result: PASS, run: "2026-01-31-ola-1"}    # written by qa:local results
```

`last_run.result` is one of `PASS`, `FAIL`, `SKIP`, `EXPECTED_FAIL`, `UNEXPECTED_PASS`. Every `roi` value except `prior_bug` is numeric.

### 1.3 Body

Given sections, never edited: `## Escenario`, `## Resultado esperado`, `## Observaciones / evidencia de la ejecucion manual`.

The observations section is NON-AUTHORITATIVE: notes of a previous manual run. They can help design a test, they never gate a case and they are never taken as a defect reference.

Added by `design`, inserted between `## Resultado esperado` and `## Observaciones / evidencia de la ejecucion manual`:

- `## Precondiciones` — business-level state, buildable from a cold environment.
- `## Pasos` — Gherkin with the structured comments `# === PRECONDITIONS ===`, `# === ACTION ===`, `# === VALIDATIONS ===`; variables in angle brackets, no hardcoded data; same-behaviour data variants as `Examples` rows of one `Scenario Outline`.
- `## Datos` — table of variable, meaning, how to obtain it. No credential value ever; credentials reach the test from the environment at run time.

Selectors and locators never enter a case file: they live inline in the KATA component written by `test-automation-local`.

## 2. ID chain

One id runs through the whole pipeline:

| Place | Form |
|---|---|
| case id | `AUT-002` |
| filename | `cases/AUT/AUT-002.md` |
| frontmatter `id` | `AUT-002` |
| automated test | `@atc('AUT-002')` (string literal, no template literal) |
| results report | key `AUT-002` in `reports/atc_results.json` |
| `last_run` and `automation.atc` | `AUT-002` |

One ATC per case id. Parameterising data inside one case is allowed; merging several case ids into one ATC is not. `check` reports an error for an id that differs from the filename, a duplicate id, and a manifest `@atc` id that looks like a case id (known prefix) but has no case file.

## 3. Verdict and lifecycle

Two orthogonal fields:

- `automatizacion` is the VERDICT. Set by `qa:local verdict`. The imported value is respected by default; ROI is computed only to justify a change.
- `estado_automatizacion` is the LIFECYCLE and means something only when the verdict is `candidate`. For `manual`, `deferred` and `no_aplica` it stays `pendiente`; `check` errors on any other value for those verdicts.

Automated runs go to `last_run`.

### 3.1 Legal lifecycle transitions (`qa:local status`)

| From | To | Fired by | When |
|---|---|---|---|
| `pendiente` | `en_automatizacion` | `test-automation-local` | start of the Code phase |
| `en_automatizacion` | `automatizado` | `qa:local results --accept` | Review ACCEPT and the case's test passed (or `EXPECTED_FAIL` for a known defect) in an ingested run |
| `en_automatizacion` | `pendiente` | `test-automation-local` | work abandoned or reverted |
| `automatizado` | (none) | | terminal |

Any other pair is refused with the list of permitted targets. `status` on a non-`candidate` case is refused.

### 3.2 Verdict changes (`qa:local verdict`)

| Change | Who | Requirement |
|---|---|---|
| `candidate` -> `manual` | `test-documentation-local` or the user | automation proved infeasible (hardware, biometrics, MAC, GPS); `--reason` required |
| `candidate` -> `deferred` | same | ROI band or Phase-0 filter; `--reason` required |
| `candidate` -> `no_aplica` | same | not applicable to the system under test; `--reason` required |
| any -> `candidate` | same | `--reason` optional |

The case must be `pendiente` for any change away from `candidate`; otherwise the script says to move it back first. `manual`, `deferred`, `no_aplica` without a reason are refused.

## 4. Known defects (after a failing automated run)

- A failing AUTOMATED run is a new finding, not a known state. Only after it fails (`last_run.result` is `FAIL` for a `candidate` case, written by `qa:local results`) may a reference be recorded.
- `qa:local defect <ID> <ref>` writes `id_defecto` and `defecto_conocido: true`, and is refused for a case without a failing automated run. The reference comes from the user, never from the observations prose and never guessed.
- The expected-failure annotation is applied only after that, and only if the user decides to keep the suite green while the defect exists. The test keeps asserting the CORRECT behaviour taken from `## Resultado esperado` (never the bug) and is annotated as an expected failure naming the reference.
- `qa:local results` maps the result for a `defecto_conocido` case: FAIL -> `EXPECTED_FAIL` (the case may still go to `automatizado`); PASS -> `UNEXPECTED_PASS`, flagged in `estado.md` as "defect probably fixed: remove the annotation, re-verify, update `id_defecto`". It is never closed automatically.
- How the expected-failure annotation composes with the `@atc` decorator is to be confirmed on the first known-defect case; if it does not compose, a status field plus a conditional skip replaces it without changing this format.

## 5. Missing preconditions and fixtures

- A case whose precondition cannot be built (a real biometric validation, a simulator that does not exist) is judged on its own text by `triage`: the proposal is `manual` or `deferred`, with a reason. The skills never invent the precondition.
- Surfaces that need a fixture the framework does not provide are marked blocked in the automation plan with the fixture named; plaintext hand-rolled calls are not a workaround.

## 6. The `qa:local` verbs (as implemented in `scripts/qa-local.ts`)

Run as `bun run qa:local <verb> [args] [options]`. No network, no Jira. Messages are in Spanish.

| Verb | Arguments and flags | Effect |
|---|---|---|
| `check` | none | Read-only. Exit 1 only when an ERROR is found; WARN and INFO exit 0. Prints `Resumen: N ERROR, N WARN, N INFO`. |
| `index` | `--date YYYY-MM-DD` | Regenerates `estado.md`: per-wave and per-prefix counts, last run, failing, `UNEXPECTED_PASS`, known defects, next 10. Never touches `prioridad-automatizacion.md`. |
| `next` | `[N]` (default 10), `--ola K`, `--prefix P` | Ordered queue of `candidate` + `pendiente` cases. |
| `verdict` | `<ID> <candidate\|manual\|deferred\|no_aplica> [--reason "..."]` | Sets `automatizacion` (and `automatizacion_motivo`). |
| `status` | `<ID> <pendiente\|en_automatizacion\|automatizado> [--atc X --spec P --surface e2e\|api]` | Legal transitions only; optionally records `automation`. |
| `defect` | `<ID> <ref>` | Records `id_defecto` and `defecto_conocido: true`. Refused unless the case is a `candidate` whose `last_run.result` is `FAIL` (run `results` first). |
| `results` | `[--file reports/atc_results.json] [--accept] [--scope S] [--date D]` | Folds PASS / FAIL / SKIP into each case's `last_run`, writes `runs/<date>-<scope>/run.json` and `run.md`. With `--accept`, moves `en_automatizacion` cases that passed (or `EXPECTED_FAIL`) to `automatizado`. A missing report file is a no-op, not an error. |
| `case new` | `<PREFIX> --title T [--tipo P --prioridad A\|M\|B --ola K --bloque B --seccion S --funcionalidad F --riesgo R --origen O --oraculo historia\|observado --escenario "..." --esperado "..."]` | Creates the next `cases/<PREFIX>/<PREFIX>-<nnn>.md` (exclusive create, one counter per prefix, zero-padded to 3) as `candidate` / `pendiente`. The prefix is 2 to 6 characters of A-Z0-9 starting with a letter. With `--dry-run` it only prints the id. Owner: `test-case-generation-local`. |
| `case confirm` | `<ID>` | `oraculo: observado` -> `confirmado`. Refused for any other value. Run only on the person's decision. |
| `bug new` | `<ID> [--title T --type Bug\|Defect\|Improvement --severity Critical\|Major\|Moderate\|Minor\|Trivial --error-type E --environment ENV --run R --visual]` | Allocates the next global `<ID>-BUG-<n>` folder in the bugs area and writes its `report.md` skeleton. With `--dry-run` it only prints the id. |
| `bug status` | `<bug id> <open\|fixed\|verified>` | Edits the `status` line of a bug report. |
| `bug check` | `[<bug id>]` | Read-only. Checks enums, links, forbidden files and secret patterns of the bug folders, printing counts and file names, never the matched value. |

Global options: `--root <dir>` (default: the `QA` folder inside `.context`), `--manifest <file>` (default `kata-manifest.json`), `--dry-run` (every writing verb prints what would change and writes nothing).

### 6.1 What `check` verifies

- ERROR: no frontmatter; missing required field; duplicate id; id different from the filename; value outside an enum; `ola` not an integer >= 0; illegal verdict/lifecycle pair; `automatizado` without `automation.atc` or with an `atc` absent from `kata-manifest.json`; `automation.surface` outside `e2e|api`; `last_run.result` outside the allowed set; a non-numeric `roi` value; a manifest `@atc` id with a known case prefix and no case file.
- ERROR: `oraculo` outside `historia|observado|confirmado`.
- WARN: a non-candidate verdict without `automatizacion_motivo`; `oraculo=observado` on a case that already left `pendiente`.
- Legacy manual-run fields are ignored: they are neither validated nor reported.
- INFO: the computed `next` order in a wave differs from `prioridad-automatizacion.md`.

### 6.2 Queue order (`next`)

Candidates with `estado_automatizacion=pendiente` and an `oraculo` other than `observado` (an inferred expected result waits for `case confirm`); nothing else filters the queue. Sorted by: `ola` ascending with `0` last; `prioridad` A before M before B; then `tipo` (contains `S` first, then contains `N`, then the rest); then id. The `tipo` rule is a substring match, the same rule the index generator used, so `NF` counts as negative and `L`-only counts as the rest. The skills never re-rank: a different order is a proposal to the user.

### 6.3 Writes

Writes are line-targeted: one frontmatter line is replaced, or one line is appended before the closing fence. Every other byte (body, other fields, line endings, quoting) is untouched; YAML is never re-serialised. A write whose value is already present prints "sin cambios". Because these files come from a converter, the converter in the QA root's `_tools/` folder MUST NOT be re-run over existing files after the first `qa:local` write: it would overwrite the fields the script manages.

## 7. ROI procedure (only to justify changing a verdict)

The imported verdict stands unless one of these holds: a hard blocker (hardware, missing fixture), the Phase-0 filter fails, or ROI clearly contradicts it. Then:

1. Phase-0 filter questions, in order: does it protect against future regressions; are there prior bugs in this area (a case with a recorded `id_defecto` counts); is it an app-level concern (accessibility, performance, XSS, responsive) rather than a feature-level case. Fail any -> `deferred`.
2. Score five factors 1-5 each: frequency, impact, stability (multipliers) and effort, dependencies (divisors, higher is worse). Scales and the normalisation constant are in `test-documentation/references/tms-conventions.md` §9; use that formula as written and ignore every TMS sentence around it.
3. Component bonus: `score * (1 + 0.2 * N)` where `N` is the number of end-to-end flows reusing the case, a qualitative estimate capped at 3. Record `bonus_n`.
4. Bands (strict): above 5.0 automate; 3.0-5.0 automate with caution; 1.5-3.0 case by case (prior bug or critical flow, else defer); 0.5-1.5 probably defer (only with a prior bug); below 0.5 defer. Map to a verdict: automate -> `candidate`; not automatable by a human-judgment or hardware reason -> `manual`; defer -> `deferred`.
5. If more than half of a triaged scope would end `candidate` or `manual`, re-apply the Phase-0 filter more strictly.
6. Write the factors under `roi` in the case (a hand edit of `roi` is allowed only together with the `qa:local verdict` call that changes the verdict) and tell the user the old verdict, the new one and the reason.

Technique-driven checks (EP, BVA, state transition, decision table, pairwise) follow `agentic-qa-core/references/test-design-doctrine.md`. Applied to given cases they produce PROPOSALS (a missing boundary or negative case); they never create case ids on their own.

## 8. Not here

- Locators, selectors, KATA component shape, fixtures, specs: `test-automation-local`.
- Run execution: `bun run test`; ingestion: `qa:local results`.
- Priority and wave definition: the user's index; this format only reads it.
- Creating cases from stories or from the built project, and the module prefixes in `prefijos.md` of the QA root: `test-case-generation-local`.
